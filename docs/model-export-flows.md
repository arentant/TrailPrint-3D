# Model export flows

The implemented flow is `mountain-trail`. City model generation is not implemented
or exposed in the UI. The app now has separate boundaries for a model workspace,
input preparation, file generation, and delivery.

## Current boundaries

- `shared/types/config.ts`: `MapModelConfig` contains map framing;
  `MountainTrailConfig` adds GPX, terrain, trail, tray, assembly, paint, and mold
  settings. `AppConfig` remains an alias for the mountain configuration, so current
  stores and saved presets keep their existing structure.
- `shared/types/export.ts`: `ExportRequestMap` defines implemented flows and their
  request types. `ExportGenerateRequest` is derived from that map, keeping the
  preload API, IPC client, and browser worker in sync. Old requests without `flow`
  still use `mountain-trail`.
- `shared/export/export-pipeline.ts`: routes requests to a registered flow and
  streams files to a sink. It checks filenames and output completeness, without
  imposing GPX, DEM, tray, or trail validation on other flows.
- `electron/main/export/mountain-trail-flow.ts`: owns the existing mountain
  validation, GPX hydration, geometry generation, optional accessories, STL
  filenames, and ZIP/standalone output metadata. The browser build continues to
  substitute its GPX, elevation, and imagery providers through Vite aliases.
- `electron/main/export/generate-model-files.ts`: registers file generators for
  both runtimes. Desktop delivery in `export-service.ts` writes a file or archive;
  `src/browser/worker.ts` creates the same output for download. Both consume the
  flow's artifact metadata and do not inspect mountain targets or filenames.
- `src/composables/useModelExport.ts`: shared busy state, preparation hooks, IPC,
  cancellation, errors, and completion handling. The mountain controller in
  `src/features/mountain-trail/useMountainTrailExport.ts` owns input validation,
  snapshots, fitting the trail, and paint-plan serialization. `useStlExport`
  remains a compatibility entry point for current controls.
- `src/workflows.ts`: registers workspace components by flow ID. `App.vue` mounts
  the default workspace; `MountainTrailWorkspace.vue` owns the current panels and
  preview. There is no flow selector while only one flow exists.

## Adding city export later

1. Define `CityMapConfig extends MapModelConfig` with city-specific inputs and
   settings. Use a separate city store; do not add mandatory city fields to the
   mountain store or saved mountain presets.
2. Define `CityMapExportRequest extends MapModelExportRequest<CityMapConfig>` with
   a required `flow: "city-map"`. Add it to `ExportRequestMap`. Keep `flow` optional
   only on the mountain request for compatibility.
3. Implement `ModelExportFlow<CityMapExportRequest>` with `describeArtifact` and
   `generateFiles`. Validate city inputs there, fetch the appropriate map data,
   and send generated bytes to the provided sink. Return file delivery metadata
   for a standalone model or ZIP metadata for a collection of parts. Use the
   common `model` progress phase or add more phases when needed.
4. Register the generator in `generate-model-files.ts`. The existing browser and
   desktop delivery adapters need no city-specific branches. If the new data
   source differs between runtimes, add the provider boundary at that time.
5. Add a city controller using `useModelExport` and a city workspace with its own
   inputs and preview. Register it in `src/workflows.ts`, then add a flow selector
   and mount the selected workspace in `App.vue` instead of the default constant.
   Use the same selected ID for its export requests. Implement city presets and
   preview APIs as needed rather than reusing the GPX-specific mountain ones.

## Verification

`npm run test:export` verifies default routing, independent inputs for a second
test-only flow, unsupported flows, file delivery contracts, sink failures, and
desktop save/cancellation cleanup using a mocked Electron dialog.
`npm run typecheck`, `npm run build`, and `npm run build:web` cover both runtimes.
`npm run test:web -- tests/browser/workflow.spec.ts` checks the existing mountain
ZIP, its printable parts, repeat downloads, and matching standalone trail STL.
